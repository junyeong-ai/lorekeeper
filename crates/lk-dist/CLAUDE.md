# lk-dist

The installation as a thing with invariants. `lore self` is the only consumer; `lore status`
reads the coherence report for its first line.

- **The artifacts are compiled in, not published beside the binary.** `embedded.rs` carries the
  agent skills, the three pipeline scripts, the rendering templates and `config.example.yaml`.
  A skill describes the commands this binary exposes and a pipeline composes them into a
  scheduled run, so both are true only of the version they shipped with — carrying them here is
  what makes "the deployed skill matches the binary" hold by construction rather than by
  remembering. The manifest is generated by `build.rs` from the directory tree, with
  `rerun-if-changed` on every file AND every directory, so a seventh skill is carried without
  anything being remembered and editing one rebuilds the binary that carries it. `templates`
  come from `lk_vault::embedded_templates` — the set a render resolves against and the set a
  deploy writes are one embedding, so a customization can be compared to what it customized.
- **Deploying is exact in both directions.** `write_tree` writes every carried file and removes
  anything else under the directory. A reference file a release dropped stays loadable by an
  agent that was told the directory is the contract, and it describes a binary that no longer
  behaves that way — so the removal is the same correctness the writing is. Removal is per-file
  against the set being written, never a recursive delete: every path comes from the embedded
  manifest, so nothing a typo could name reaches `remove_dir_all`. The config directory is the
  exception and is written file by file, because it also holds the user's own `config.yaml`.
- **The check and the prune are ONE rule, and neither follows a link.** They compare file
  identity, not paths: while only the prune did, the file it correctly kept on a case-folding
  volume was what the check counted as an extra — drift reported forever, naming a repair that
  could not remove it, which is the same shape as a deploy that cannot fix what status counts.
  `identity` reads `symlink_metadata`, so a link is itself rather than what it names, and the
  walk counts everything that is not a directory: an agent loads a symlink exactly like a file,
  and following it put one into the expected set where it survived the prune and was skipped by
  the check at once.
- **The prune compares FILES, not names.** A rename onto an entry differing only in case keeps
  that entry's spelling on macOS and Windows, so the path the walk reads back is not the path
  that was written — and `write_tree` deleted the file it had just created, exited 0, and left a
  skill pointing at a reference that was gone. `canonicalize` cannot answer it (macOS `realpath`
  leaves case exactly as given); the inode can, exactly. CI runs a case-sensitive volume, so no
  gate here could have caught it — which is why the test proves the mechanism with a hardlink.
- **A skill this binary no longer carries is removed, and a prefix is not provenance.** Both
  the comparison and the deploy used to iterate what the binary HAS, so a skill dropped or
  renamed between releases stayed on disk and an agent kept loading it and following
  instructions for commands that no longer exist. The prune runs against the set the last
  deploy RECORDED writing (`<config_dir>/deployed-skills`) — the only thing on disk that tells
  a directory this tool created from one the user wrote. Pruning on the `lore-` prefix instead
  deleted a hand-written `lore-standup/` recursively and unannounced, on the first unattended
  update, because that is the natural prefix for a skill about this tool and the one the
  documentation trains people on. The record is PER LEVEL and is written only for a level a
  deploy actually reached: it is a claim about what happened, not about what the binary holds,
  so `--skills none` claims nothing and a name written at one level authorises no removal at
  another. An installation with no record for a level prunes nothing there, and every removal
  is NAMED — on the failure path too, since that is where the user most needs to know a
  directory is gone and an error saying only "permission denied" reads as "nothing happened".
- **The data directory an installer named is written down.** `--data-dir` reached exactly one
  `self deploy` and was recorded nowhere, so every later `self status` looked in the default
  directory, found nothing and reported the installation coherent — while `self update` deployed
  a second copy there and left the scheduled job firing the first one forever. `deploy` records
  it at `<config_dir>/data-dir`; `data_dir()` reads it below the environment, which is an
  explicit instruction for this run, and above the defaults, which are only a guess.
- **A deployed file's EXECUTE BIT is part of the artifact.** A scheduler executes a pipeline
  rather than reading it, so a copy that lost the bit fails every night while a byte-only check
  reported the installation healthy and never named the repair. The bit and nothing else:
  comparing the full mode would report permanent drift on a volume that carries no Unix
  permissions, which `self deploy` could not clear — the unrepairable-drift shape rather than a
  finding.
- **One report names ONE repair.** `lore status` and `lore self status` read the same
  `InstallationReport`, so the command it names is asked of the report rather than written at
  each front door — two doors naming different repairs for one verdict is a disagreement a
  reader has no way to settle. Where the SCHEMA is the only difference the answer is `lore
  schema`: it is the one artifact inside the user's vault, a deploy writes it best-effort, and
  on an unreachable vault `lore self deploy` exits 0 having only warned while the `!` never
  clears.
- **`deploy` repairs everything `status` counts**, `AGENTS.md` included — rendered in process,
  because this binary owns the page-format table it is generated from. A deploy that skipped it
  named itself as the remedy for a difference it could not remove, and the exit code never
  cleared.
- **The PROJECT level writes and never deletes, and the check judges it on exactly that.**
  Deleting is the half that costs unrecoverable work; overwriting is what a redeploy is for and
  is recoverable wherever the files are under version control. The guard that answers "is this
  the checkout I was built from" is compile-time, so a released binary can never ask it — and no
  discriminator on disk tells this tool's earlier output from a checkout's tracked files.
  `Prune::for_level` is the whole rule, because it is a property of the LEVEL and never of the
  invocation: keyed off the flag a caller passed, `--skills project` protected a directory that
  the bare `lore self deploy` inside `lore self update` then swept, so the protection lasted
  until the first unattended update and no further. And the check follows the prune there as it
  does everywhere — an extra file and a retired directory at that level are not counted, since
  drift whose named repair declines to remove it is the unclearable loop, and the file it would
  name is the one this level exists to protect. What the binary DOES carry is still compared,
  so an edited `SKILL.md` is reported and rewritten.
- **Everything this tool wrote is removed by the uninstall, records included.** Leaving the
  `data-dir` record behind meant a later bare `self deploy` resurrected the very directory the
  uninstall had removed, in preference to the default, with nothing said.
- **Regenerating `AGENTS.md` is best-effort.** It runs after everything a deploy OWNS has landed
  and it writes into the user's VAULT — a drive not mounted or a vault the process cannot reach
  would otherwise report a failed install for one that is complete, and the advised re-run would
  fail identically forever.
- **A group nothing deployed is absent, not stale.** An install that deliberately took no
  skills, or a machine with no scheduler and therefore no pipelines, is coherent. `deploy`
  writes skills where they already are and creates a set nowhere else unless `--skills` names a
  level, so an update never gives an installation artifacts it declined.
- **Coherence is a comparison of bytes and mode, never a version string.** `ArtifactState` is
  `Current`, `Modified`, `Absent` or `Retired` — the deployed copy and the binary are one
  artifact, so "the same" is decidable exactly. A hand edit and a copy left by an older
  release are the same state on purpose: both mean the bytes are not what this binary would
  write, and both are repaired by the same command.
- **`SchemaState` is the one artifact inside the user's vault.** `<wiki>/AGENTS.md` is rendered
  from the binary's page-format table and the user's config, and nothing rejects a stale one the
  way the vault rejects a broken link — so the page declares its `generator` and this compares
  it. The path is passed in rather than resolved here: which page is the contract depends on the
  vault the config names, and this crate knows nothing about vaults.
- **`ReleaseTarget::ALL` is the one target table.** The triple is the `{target}` in
  `lore-v{version}-{target}`, and the `uname` spellings are how `scripts/install.sh` selects one
  before any binary exists. `tests/carried.rs` holds all three copies together — this table, the
  release matrix, and the installer's `case` arms — and reads the arms with a parse that fails
  closed, because a mapping half-read compares as a mapping that disagrees. Self-update support
  is DERIVED from the archive format rather than listed: Windows ships a `.zip` and cannot
  rename over a running executable, so it is refused and named `install.ps1`.
- **The API settles which release is latest.** The `/releases/latest` web view is a cache that
  trails it by minutes right after a release — exactly when someone updates — so it answers only
  where the API could not, and `Provenance` carries which one did so the caller can say so.
- **Precedence clears build metadata.** `Version`'s own `Ord` orders by it, because `Ord` must
  agree with `Eq`; the specification says it carries no precedence. Comparing the pair with that
  field cleared is the crate's ordering for everything that counts, minus the one field that
  must not — without it `1.2.3+build.5` reads as neither older than nor the same as `1.2.3`,
  which resolves to an update onto the version already installed.
- **A refusal is not an approximation.** A channel answering older than the running binary is
  refused: a rollback and a stale read are the same shape, and going back takes an explicit
  `--version`, which is deliberate in either direction.
- **Nothing writes a path an archive chose.** `read_from_tar_gz` returns one member the CALLER
  named and skips everything else, so there is no `../`, no absolute path and no symlink rule to
  get right on bytes fetched from the network. The checksum is computed in-process (`sha2`),
  never shelled out to a `sha256sum`/`shasum` that differs between platforms and is guaranteed
  on none; the sidecar's name is checked when present, so one fetched for another asset fails
  rather than passing on a digest that describes something else.
- **An attestation is checked on a file nobody else could reach.** `temp_dir()` is
  world-writable and the archive's name is fully predictable, and `fs::write` follows symlinks —
  a pre-created link at that path had whatever it pointed at truncated, under `sudo` anywhere on
  the system. Staging inside a directory created with `create_dir`, which fails if it exists,
  closes that and the second hole with it: the file `gh` verifies can no longer be swapped
  between the write and the check for a different, genuinely attested archive.
- **The swap proves the result before letting go of the previous bytes.** `install_binary`
  publishes through `lk_core::fs::write_atomic` — the workspace's one temp-fsync-rename writer,
  so the destination is never partial and the kernel keeps the running inode alive — then runs
  the new file and compares the version it reports. That is the only check answering for the
  kernel, the architecture and the platform's code signing at once, and an installation whose
  binary does not run has no way left to repair itself, so a mismatch puts the previous bytes
  back. The replacement keeps the permissions the binary already carried rather than taking
  whatever the umask grants a new file.
