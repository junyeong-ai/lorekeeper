# Proposal 0003 — Consolidation & Distribution

## Summary

Collapse the system's four surfaces into two, under one name, shipped by one
installer:

- **One Rust workspace — `Lorekeeper`** (binary `lk`). Absorbs the standalone
  `wikigraph` as the `lk-graph` crate so all domain logic (slug, frontmatter,
  wikilink, vault paths) lives once in `lk-core`.
- **One Claude Code skill — `/wiki`** (absorbs `/lore-process` as its `process`
  command). Shipped *from the Lorekeeper repo*, installed by the same
  `scripts/install.sh`.

The binary and skill are two halves of one contract; co-distribution keeps them
versionlocked. A user runs `scripts/install.sh` once and has the whole system.

## Why consolidate: the split is duplicative, not separative

The deterministic/semantic boundary (Rust vs skill, from Proposal 0001) is a
real capability boundary and stays. But the *within-Rust* split into two
binaries (`wikigraph` read-only analyzer, `Lorekeeper` stateful writer) is
accidental — `wikigraph` was an earlier experiment — and it already duplicates
domain logic with **divergent rules**:

```
lk-core   slugify()       : lowercase → split → join("-") → keep [alnum-]   (NO unicode norm)
wikigraph normalize_slug(): NFKC (default) → trim → ...                     (unicode norm)
```

These disagree on composed/decomposed Hangul and full-width characters —
exactly what arrives from Slack/Gmail in a CJK environment. Concrete failure:
the writer names a file with its slug; the analyzer normalizes the same name
differently and reports the page as a **false orphan / false broken-link**.
Two independent implementations of the same domain rule is a standing bug
source. One `lk-core` eliminates the entire class.

Other duplications today: frontmatter parsing, wikilink extraction, vault-path
construction — each implemented in both projects.

│   ├── lk-llm/                  # queue / anthropic / noop providers

Binary surface:

```
lk ingest [source]          lk schema              lk validate
lk maintenance              lk graph lint          lk graph hubs
lk graph orphans            lk graph broken        lk graph cluster
lk graph suggest-links      lk graph index-sync    lk graph normalize
lk graph export
```

`lk-graph` depends only on `lk-core` + `petgraph`; it never pulls the
reqwest/tokio/google/slack stack. `lk graph lint --root /any/vault` still works
on any Obsidian vault, so the general-analyzer use case is preserved — the user
just installs `lk` instead of a separate `wikigraph`.

Skill surface:

```
/wiki add <source>     manual ad-hoc ingest
/wiki query <q>        answer + compound to explorations/
/wiki audit            semantic lint (calls `lk graph lint` + `lk graph suggest-links`)
/wiki status           stats
/wiki process          drain the queue
```

Four surfaces (`wiki` skill, `lore-process` skill, `wikigraph`, `Lorekeeper`)
become two (`lk` binary, `/wiki` skill).

## Distribution: Lorekeeper ships the skill

### The contract that makes co-distribution mandatory

The skill and binary are not independent tools that happen to cooperate — they
share three contracts:

1. **Queue task schema** — `lk ingest` writes JSONL; `/wiki process` reads it.
   Includes `target.anchor` (Proposal 0002). A schema change must land in both
   at once.
2. **`wiki/AGENTS.md` format** — generated by `lk schema`, consumed by the
   skill for every page format and heading.
3. **CLI surface** — the skill calls `lk graph lint`, `lk schema`,
   `lk graph suggest-links` via Bash.

If the skill ships separately and drifts a version from the binary, all three
contracts can silently break. Shipping both from one repo, installed together,
makes version skew structurally impossible. This is the long-term argument:
**co-distribution is how you keep a two-process contract honest.**

### `scripts/install.sh` (one command, whole system)

```
1. Build + install binary:   cargo install --path crates/lk-cli   (→ ~/.local/bin/lk)
2. Install the skill:         link skills/wiki → ~/.claude/skills/wiki
                              (symlink so `git pull` updates the skill in place;
                               --copy flag for users who don't track the repo)
3. Bootstrap:                 print next steps —
                              cp config.example.yaml config.yaml; edit identity;
                              lk schema; lk validate
```

`uninstall.sh` removes the binary and the skill link. Idempotent; safe to
re-run.

### `.claude-plugin/marketplace.json` (team sharing)

The repo is also a Claude Code plugin. Teammates who live in Claude Code add
the marketplace and install the skill without cloning — and the plugin can
declare the `lk` binary as a prerequisite. The two distribution paths serve two
audiences from one source:

- **CLI-first / repo-tracking** → `scripts/install.sh` (binary + linked skill)
- **Claude-Code-first / team** → plugin marketplace (skill) + `cargo install` or
  a released binary (binary)

Both install the same `skills/wiki/SKILL.md` from the same repo, so neither can
drift from the binary.

### Version coupling check

`lk --version` and the skill carry the same repo version. `/wiki` runs
`lk --version` at start and warns if the binary predates the skill's expected
contract (a one-line guard, not a framework). With install.sh this never
triggers; it only catches a hand-mismatched setup.

## Naming authority (this proposal owns names)

| Axis | Value |
|---|---|
| Repo / product | `Lorekeeper` |
| Binary | `lk` |
| Crates | `lk-core`, `lk-source`, `lk-pipeline`, `lk-vault`, `lk-llm`, `lk-graph`, `lk-cli` |
| State dir | `.lorekeeper/` |
| Schema generator | `lk schema` |
| Skill | `/wiki` — the operation domain noun; what the user does to their vault. (The product is Lorekeeper; the verb stays `/wiki` for discoverability.) |
| Queue dir | `.lorekeeper/queue/` |

Proposal 0001 (the `lk-*` crates and `lk ingest`) and Proposal 0002 (`lk schema`,
`TaskTarget.anchor`, crate references) inherit these names. No `wikigraph`
identifiers survive once it is absorbed — the consolidation is total, with no
compatibility aliases.

## Migration

1. **Settle the workspace name** `Lorekeeper`; crates `lk-*`; binary `lk`; state
   dir `.lorekeeper/`. Every path/string uses these names.
2. **Absorb `wikigraph`** into `crates/lk-graph`: move `graph.rs` / `cluster.rs`
   / `index.rs`; delete its `parse.rs` and `normalize.rs` and rewire them to
   `lk-core`'s slugify / frontmatter / wikilink (the dedup). Port its tests into
   `lk-graph`. Delete the standalone `wikigraph` repo.
3. **Expose** graph commands under `lk graph *` in `lk-cli`.
4. **Merge skills**: fold `/lore-process` into `/wiki` as the `process` command;
   move `skills/wiki/SKILL.md` into the repo; delete `~/.claude/skills/lore-process`.
5. **Add `.claude-plugin/marketplace.json`** referencing `skills/wiki`.
6. **Extend `install.sh`** to install binary + link skill; mirror in
   `install.ps1`; update `uninstall.*`.
7. Apply Proposal 0002 (generated `AGENTS.md`, compounding query, audit,
   locale-resolved `target.anchor`) on the consolidated names.

The vault is small; the `.lorekeeper/` state dir needs no data migration
framework — a documented one-liner suffices for any housekeeping.

## Non-Goals

- Keeping any `wikigraph` name as an alias (clean consolidation only).
- A standalone ultralight graph binary (crate isolation already keeps
  `lk graph` dependency-light; a hypothetical 2 MB standalone is YAGNI).
- A plugin auto-installing the binary (the binary is `cargo install` / released
  artifact; the plugin declares it as a prerequisite, doesn't bundle it).
