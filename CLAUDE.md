# Lorekeeper

Config-driven knowledge ingestion pipeline for Obsidian wikis. A Rust CLI (`lore`)
collects daily data from heterogeneous sources, deduplicates, classifies, extracts
concepts, and writes structured markdown pages. Includes graph analysis for wiki
structural health.

## Architecture

```
Data Sources              lore (Rust CLI)            Obsidian Vault (vault.dirs.*)
────────────              ───────────────            ──────────────────────────────
Google Drive ──┐          ┌─ Extract (per-source)    <daily>/{source-id}/
Gmail ─────────┤          ├─ Normalize → Event       <personal>/work-log/
Slack ─────────┼─ config ─┤  Collapse dup (intra-batch)<personal>/{weekly,monthly,quarterly,annual}/
Jira ──────────┤  .yaml   ├─ Classify (labels)       <synthesis>/{weekly}/
Calendar ──────┤          ├─ Concepts (LLM)          <wiki>/concepts/
RSS/Atom ──────┤          ├─ Render (templates)      <wiki>/documents/
Manual inbox ──┘          ├─ Wiki index (catalog)    <wiki>/index.md (by-topic)
                          ├─ Wiki log (timeline)     <wiki>/log.md (by-time)
                          ├─ Wiki map (clusters)     <wiki>/map.md (by-citation)
                          ├─ Resolve (name → page)
                          └─ Graph (lint, cluster,   <wiki>/AGENTS.md
                               suggest-links, merge,
                               backlinks-sync, …)
```

## Workspace

Each crate has its own `CLAUDE.md` with the invariants for working inside it
(loaded on demand when you open files there).

```
crates/
  lk-core/      Domain types, config, i18n, slugify (NFKC), frontmatter, link, vault paths, atomic write
  lk-vault/     Obsidian vault I/O: atomic write, templates (embedded), ingest log
  lk-source/    Source adapters + factory, markdown normalization (ADF/HTML/Slack→MD)
  lk-pipeline/  Pipeline (per-source plan), intra-batch dedup, classify, concepts, synthesis
  lk-queue/     Semantic task queue: LlmClient trait, QueueLlmClient (JSONL), noop (+ mock for tests)
  lk-graph/     Link graph analysis: lint, hubs, cluster, suggest-links (no HTTP/async)
  lk-task/      The intent plane: the task board's grammar, its state machine, the transition
                log, and the observation a completed task becomes
  lk-dist/      The installation as a thing with invariants: the release-target table, release
                resolution/download/verification, the artifacts the binary carries, and the
                coherence report `lore self` acts on
  lk-cli/       Binary `lore` — one module per subcommand under commands/
templates/      Jinja2 markdown templates (.md.jinja), compiled into the binary
```

## Development

```bash
scripts/check.sh                   # every gate CI runs, failing on the first that does
cargo check                        # type check
cargo fmt                          # format
lore validate                      # verify config.yaml + source params
lore ingest ai-news                # run a single source
lore schema                        # generate <wiki>/AGENTS.md
lore wiki concepts                 # list all concept pages
lore resolve <name>                # which concept page a name addresses (0 owned/1 absent/2 ambiguous)
lore graph lint                    # structural health check
lore doctor                        # page contracts: text cleanliness, unanswered sections, credentials
lore queue status                  # classify pending LLM tasks (current/stale/missing)
lore queue count                   # bare integer: current tasks (machine contract for scripts)
lore queue apply                   # materialize drained concept results into pages + links
lore config vault-root             # bare path (machine contract for scripts)
lore config schema-path            # bare path to the vault's AGENTS.md (the wiki dir is configurable)
lore status                        # one line per subsystem, each naming the command that owns it
lore self status                   # is every deployed copy still the one this binary carries
lore self deploy                   # rewrite the skills, pipelines, templates and config example
lore self update                   # replace the binary with a release, then redeploy
lore agenda                        # the day read off the task board (a view; writes nothing)
lore task add "…" / done / sync    # the board: intent in, completed work out
lore task propose                  # what the sources say is still open, offered — never committed
lore task remind add "…" --at 15:00  # say something at a time (fired by a timer, off the board)
lore agenda --json                 # the day as a contract, for a skill rather than an eye
lore task rollover --closing yesterday  # close the day that ended — carry what is still committed
```

## Config

User settings in `config.yaml` (gitignored); copy `config.example.yaml`.
Auto-discovered: `./config.yaml` → `~/.config/lorekeeper/config.yaml`.
`vault.root` resolves relative to the config file's directory, not the CWD.

## Cross-cutting invariants

- **Source ID = vault directory**: the key under `sources:` becomes `<daily>/{id}/`. Must not contain `/` or `\`, and must not be `.` or `..`.
- **Vault directories configurable**: all top-level vault paths (`<daily>`, `<personal>`, `<synthesis>`, `<wiki>`) are set via `vault.dirs.*` in config.yaml. Their fixed leaf subdirectories (`concepts`, `documents`, `explorations`, `work-log`) are single-sourced as `lk_core::vault_path` constants. Every crate builds paths through `VaultPath` builders or those constants — never an inline string literal.
- **Date derivation**: `timestamp.to_zoned(vault.timezone()).date()` — always via configured timezone, never UTC.
- **Multi-date batches**: events spanning several dates produce one `<daily>/` page per date.
- **Ownership decided by the adapter**: each source sets `RawItem::is_self` by exact-matching its structured authorship field against the user — Gmail `From`/Calendar organizer-or-attendee vs `identity.email`, Slack author vs `identity.slack_id`, Jira assignee vs the authenticated `/myself` account. `is_personal` = `is_self && source ∈ personal.tracked_sources` (so an absent `personal:` module means nothing is personal). The pipeline never infers ownership from free-form text, so recipients/CCs/mentions never pollute the personal work-log or reviews.
- **The personal module is optional; the core is domain-neutral.** `config.personal` (`Option<PersonalConfig>`) owns the entire personal-productivity subsystem: the work-log, the weekly/monthly/quarterly/annual reviews, the contribution taxonomy (`performance_categories` + maps + the classify `performance_category` bridge), and `tracked_sources` (which sources count as "mine"). ABSENT (the default) = a pure knowledge engine: no work-log, no reviews, no `is_personal`, and `lore schema` omits those page formats from `AGENTS.md`. Every personal behavior is gated on `config.personal.is_some()`; nothing in the ingest→concept→wiki→graph core depends on it. Cross-source weekly *synthesis* (themes, `<synthesis>/weekly/`) is core knowledge synthesis and stays regardless.
- **The vault is realized-only — forecasts never materialize** (`event.date > today`): a date after today is a FORECAST, so `Pipeline::plan` writes NO page for it (no daily page, concepts, or citations) — one chokepoint that keeps every downstream consumer clean by construction. Two defense-in-depth gates enforce the same `today` boundary (wall-clock, vault tz, independent of `--date`) off the page-render path: `render_work_log` drops future events and `Synthesizer::read_date_range` caps reads at today. A forecast becomes knowledge once its date arrives. `is_personal` is time-agnostic.
- **Atlassian auth is one facade over named instances.** `credentials.atlassian` is a MAP of instances (`default`, `cloud`, `onprem`, …) because one org routinely runs a Cloud tenant *and* an on-prem Data Center wiki; a source picks one with its typed `instance` field (optional when only one exists) — credential routing is a source-level concern the factory resolves, so it sits beside `classify` rather than inside the untyped `params`. Each instance declares `method`: `oauth` (Cloud gateway), `scoped-token` (Cloud gateway, Basic), `api-token` (Cloud site, Basic), or `pat` (Data Center Bearer). Each variant carries only its own fields, so an impossible pairing is unrepresentable — and **`Deployment` (Cloud vs DataCenter) is DERIVED from the method, never configured**, since each credential form exists on exactly one deployment. `AtlassianAuth` answers the only three questions adapters ask (base URL, `Authorization` header, REST dialect); adapters never branch on the method, so a new method is a change in `lk-source::atlassian` alone. **The method chooses the HOST; an IP allowlist judges the PRINCIPAL.** Cloud answers at the site (`{org}.atlassian.net`) and at the gateway (`api.atlassian.com`); an account token comes in two shapes and each is honored by exactly one — classic at the site, scoped at the gateway — while the site does not refuse a scoped token so much as ignore it, an anonymous 401 naming nothing. The allowlist is a separate axis and cuts across both: it answers `403 "your IP address is not listed"` to an account token at EITHER host while admitting an org-approved app from the same address at the same moment, so on such an instance `oauth` is the only method that reaches the API from an address the list does not name. The token methods are for instances without a list, or for addresses on one. `AtlassianAuth::explain_failure` names the causes a given failure could have at the point of it — keyed on the CONFIGURED METHOD and the status code, never on matching text in the provider's body, so an OAuth 403 is never called an allowlist problem and a token's 403 names the allowlist beside the alternatives rather than as the answer. Knowing only the method and the status, naming the candidates is the most it can honestly do. **Atlassian ROTATES refresh tokens** (each refresh invalidates the one it used), so: the successor is persisted to `credentials.json` as part of completing a refresh; one `AtlassianAuth` per instance is SHARED across every adapter in a run (two would invalidate each other mid-run); the refresh request is deliberately NOT retried (a retry after a committed rotation strands the grant permanently, whereas failing the run self-heals next time); and Lorekeeper needs its OWN OAuth app — a grant shared with another client breaks both daily.
- **A concept's evidence is the set of pages citing it, and `backlinks-sync` is its sole deriver.** Three things on the page answer to that set — the `## Sources` body, `source_count`, and the `llm_inputs.synthesis` input its `## Synthesis` is owed against — so one sweep writes all three or none. Ingest writes none of them: it renders the sources heading empty, re-emits whatever count the page already carries (`0` on a page it CREATES), and carries the recorded markers through unchanged, because a render cannot see the link graph and so has no standing to judge them. The digest is over the SET, never the rendered citation list: a source page RETITLED changes how a citation reads without changing what it is, so its line is corrected while the synthesis stays answered. A concept NOTHING cites records no input and is owed nothing — there is no evidence to answer to — while one whose last citation was deleted keeps the input it already answered, since no rewrite could improve on it from a set that is now empty.
- **Whoever fills a section stamps its marker in the same edit.** `llm_cache` decides a section's fate purely on `llm_inputs.<key>_done`, never on whether the body looks filled — so a section written without one is erased by the next render and its task re-enqueued forever. `lk_vault::set_llm_input` is the single writer for those nested markers (`set_frontmatter_field` owns top-level keys and cannot reach them), and `record_llm_input` is the one place allowed to ADD the mapping — a marker stamped where the pipeline never rendered one would claim a render that never happened, but a concept's synthesis input is DERIVED by `backlinks-sync`, so there the writer establishes it rather than a reader hoping to find it.
- **One question about a name, one answer, both planes.** `lk_core::concept::ConceptRegistry` maps every name a concept page answers to — its own address, its title, each alias — through `identity_key`, and it is what the ingest pipeline routes an extraction by AND what `lore resolve` answers a skill with before that skill writes a page. Computing it twice is what lets the write path fold `VectorDB` onto `vector-db` while the read path calls the name free and mints a rival beside it. The match is EXACT on identity, which folds spelling and nothing else, so `k8s` does not find `kubernetes` — that judgment is about meaning and stays with `/lore-wiki audit`. A name more than one page answers to is the vault defect `lore graph lint` reports; a citation written now still has to land somewhere, so the answer carries both the destination and every claimant rather than settling it in silence.
- **A concept's slug is resolved once, never re-derived.** A page's id is NOT always `slugify(title)`: a renamed or merged concept keeps its original id and records the other names as aliases, which is what keeps existing citations resolving. `ConceptDrafts` builds an alias index from the vault and returns the resolved `ConceptIdentity` from every merge; `render::concept_links` renders from THAT, so a citation and the page it points at cannot disagree. Computing the slug in both places is what mints a second page beside the canonical one and splits its citations. The index seeds each page's own slug before any name, so a page owns its address even when no name of its own reproduces it — `lore graph lint` reports two pages answering to one name as a duplicate.
- **`day_window` bounds land on civil midnight**, with padding rounded outward to whole days. The pipeline renders a daily page for every date a batch touches and a complete-refetch source renders it from the fetch alone, so a window ending mid-day hands it a PARTIAL day that overwrites that date's page with the fragment. Absolute-hour arithmetic cannot guarantee this: on a DST fall-back day `day_start - 24h` lands an hour AFTER the previous midnight.
- **The queue carries requests one way and VALUES back.** A drained task that writes one section of one page writes it directly; concept extraction does not. Its output lands on pages SHARED between origin pages, under merge rules (preserved `## Synthesis`, aliases, established category, `source_count`) that already exist as tested Rust in `ConceptDrafts` — so `/lore-process` reports the concepts it found — with a grounding sentence used only when a page is CREATED — to `queue/results/*.json` and `lore queue apply` materializes them through that same path, rendering the origin page's links with the same `concept_links` builder. One implementation of the merge, extraction reduced to a pure function of the page it read, and no cross-page write set for a drain to collide on. A missing anchor section is an ERROR there, never a silent no-op: `replace_section` returns the page unchanged when the heading is absent, which would delete the result and report success.
- **A queued task's fate is decided deterministically, never by an LLM session.** `lore queue status` classifies each pending task in tested Rust from two independent facts on its target page: is the page still the one the task was made for (`llm_inputs.<key>` vs `cache_hash` — else `stale`, or `missing-target` if the page is gone), and has this exact input already been answered (`llm_inputs.<key>_done` — then `done`). Only a task passing the first and failing the second is WORK — and then only if the page still carries the SECTION it names, since a page's headings come from the render and an anchor the page lacks means the heading vocabulary changed since (a `vault.locale` switch does exactly this without touching the concept input hash, which does not include locale); waiting cannot bring it back, and dropping loses nothing because the absent completion marker makes the next ingest re-enqueue the work under the heading the page now has — except for a concept synthesis, which no ingest enqueues: `lore graph backlinks-sync` is its only source, and it re-queues on the same marker, so the work returns from there instead. Work is what `/lore-process` acts on and the only thing `lore queue count` counts; a drained RESULT is classified by the same code but never asks the completion question, because a task is a request while a result is the answer in flight — and for concepts the marker is written by the very edit that applies it — a scheduled pipeline must not spend a session on a queue holding nothing to do. `lore queue prune` applies the same classification destructively: dead tasks are dropped, an answered task is kept so the run's record stays whole, and a run whose every remaining task is answered is retired to `processed/` exactly as a drain retires a finished run — otherwise nothing would ever archive it and it would sit in the queue warning about pending work forever.
- **Per-item isolation stops where NOTHING was reached.** An adapter that fetches many independent things (RSS feeds, Drive files) warns past a single failure so one broken item doesn't cost the others their day — but if EVERY attempt failed it returns an error, because an empty success is indistinguishable from a quiet day and the ingest log records only that one bit. `lore health` reads that log as its sole evidence a source is alive, so swallowing a total outage would let a source whose URLs have all moved report fresh forever. `lk_source::require_any_observation` is the single rule and it takes what was OBSERVED, never a count of failures and never a subtraction — "read" covers usable as well as reachable, since a file whose metadata will not parse is as absent as one that would not download. An empty listing (nothing attempted) stays a success, and so does an entry dated for another day: RSS decides mapping and windowing separately so a quiet feed can never look like a broken one.
- **Retention prunes history; it may not prune state.** The ingest log is both a run history and the store `find_last_collection` reads, so `lore maintenance` keeps each source's newest COLLECTED entry whatever its age — the exact line that reader returns, not merely the newest one, since a source failing daily has a recent failure the reader skips in front of the older success it wants. Without that, every entry for a source dead longer than the horizon disappears and it stops reading `stale` (non-zero) and starts reading "never ingested" (silent without `--strict`) — the alarm turning itself off exactly as the problem ages. `--dry-run` reports the same counts and deletes nothing, like every other mutating command.
- **Idempotent ingest**: plan → write daily/concept → work-log → flush LLM queue → log, then an archive hook for the `manual` source. There is no commit step: a daily page is re-rendered in full each run, so any write or flush failure just leaves the affected pages for the next run to reproduce byte-identically. The `manual` archive runs only when every vault write and the queue flush succeeded — its knowledge is durably materialized by then, so another source's fetch failure doesn't block it, while any write/flush failure leaves inbox files for retry.
- **A living document carries its version in its identity.** Every other source reads immutable items (a sent mail, a posted message); a Confluence page is edited in place. So the confluence adapter's `external_id` is `confluence:{page_id}:v{version}` — an unchanged page re-fetched tomorrow reproduces the same id (dedup absorbs it, the `llm_inputs` hash keeps the LLM idle), while an edit mints a NEW event that flows through summarize/concept extraction again. Freshness therefore falls out of the existing materialized-view machinery with no reconciliation pass. Ownership is **last-writer**, not contributor: `is_self` compares the *current version's* author to the authenticated account, because CQL's `contributor = currentUser()` also matches pages someone else last edited — knowledge to read, never the user's own work-log entry.
- **Intent is a third plane, joined to the other two at exactly two points.** Everything else here runs one direction — a source is observed, the observation becomes a page, the pages become knowledge — and every invariant enforces it: the vault is realized-only, forecasts never materialize, the work-log records PERFORMED contribution. A task is the other direction: a claim about the future, authored by a person, whose state changes by their hand rather than by a re-fetch. So it is not a new kind of page in the existing plane. An observation may PROPOSE a task and never creates one — structurally where a source's own field answers it (a Jira issue assigned and not `done`, via `RawItem::open_work`), by declared judgment where only prose could (`lore task candidate`, for the sources `personal.tasks.propose_from` names), landing as a `Proposed` line whose two answers already existed: drag it to accept, `lore task drop` to decline. A completed task BECOMES an observation, through a built-in `tasks` SOURCE that reads the transition log — which is why there is no archival machinery at all, the daily page, the work-log, the contribution categories, the concept extraction and every review already consume events. That closes the loop the rest of this tool only half serves: today the vault compounds what was READ, and a completion's closing note is how what was DONE compounds too. Nothing forward-looking is ever materialized — only a completion becomes an event, dated when it happened, never when it was due. `<personal>/tasks.md` is the truth rather than a rendering of a store kept elsewhere, because the vault is the product: a box ticked on a phone has to count, and the state machine reads the section HEADING a line sits under, so dragging it in an editor is the state change. Where a task CAME FROM — the Slack thread, the Jira issue, the mail, the meeting — is an absolute URL in its visible title (`lore task add --link`), never a vault path: it is copied verbatim onto the archive page, so a relative destination would resolve somewhere else from there; the board is a valid citation SOURCE, so a vault destination would make a concept's evidence appear when a task was written down and vanish when it was finished; and the vault is realized-only, so the page a forward-looking task is about may not exist yet. `lk_core::link::is_external` keeps a scheme-bearing destination out of the graph entirely, which is what makes all three go away at once. The board declares `type: task-board` and the graph excludes that format from both link views and from what may cite a concept — it is the one managed page that is forward-looking and that SHRINKS, so counting it as evidence would make a concept's `source_count` appear when a to-do was written down and disappear when it was finished.
- **The installation declares itself the way the vault does.** Every page states its format and what it was derived from, a command checks those declarations, and another repairs what the check reports — and that discipline used to stop at the vault boundary, so a scheduled install could fall a year behind while `lore health` reported green (it measures ingested-data freshness, the only thing that declared itself). The skills, the pipeline scripts, the rendering templates and the config example are therefore COMPILED INTO the binary (`lk-dist::embedded`, collected by a build script from the tree rather than a list), so they cannot be a different version from it — one artifact, and `lore self deploy` writes the copies. What is left to check is whether a deployed copy still equals what the binary carries, which is a BYTE comparison rather than a version string and so has no reading in which a copy is merely probably current; an absent group (an install that took no skills, a machine with no scheduler) is absent, not stale. `<wiki>/AGENTS.md` is the one managed artifact that lives in the user's vault, and it is rendered from the binary's page-format table — nothing rejects a stale one the way the vault rejects a broken link, so it carries a `generator` frontmatter key and `lore self update` re-runs `lore schema` through the NEW binary as part of the update. `lore status` composes this with source currency, the queue, page contracts and the graph verdict — each computed by the code its own command exits on — and reports without gating, because the command that owns a subsystem is the one whose exit code answers for it.
- **An update is refused rather than approximated.** The API settles which release is latest and the `/releases/latest` web view answers only where the API could not — the view is a cache that trails by minutes right after a release, which is exactly when someone updates, and an answer taken from it says so. Precedence is semver's with build metadata cleared (`Version`'s own `Ord` orders by it, because `Ord` must agree with `Eq`), so `1.2.3+build.5` and `1.2.3` are one version; a channel answering older than the running binary is REFUSED, since a rollback and a stale read are the same shape, and going back takes an explicit `--version`. The archive is verified against its published digest in-process (`sha2`, never a shelled-out `shasum` that may not exist), one named member is read out of it rather than unpacked (nothing writes a path the archive chose, so there is no traversal rule to get right), and the swap keeps the previous bytes until the replacement has PROVEN it runs and reports the requested version — the only check that answers for the kernel, the architecture and the platform's code signing at once. Windows is refused outright and named `install.ps1`, because it cannot rename over a running executable and a half-implemented swap leaves no binary at all. An update also refuses while the queue holds work: a task is written by one build and answered under whichever build's skills are deployed when the drain runs.
- **The scheduled pipelines compose `lore`; they never orchestrate inside it.** `scripts/lore-pipeline.sh` holds the shared stage runner and the commands that exist so a script or an agent never greps prose (`config vault-root`, `config schema-path`, `queue count`); `lore-daily.sh` and `lore-weekly.sh` are the stage lists. Putting `claude -p` invocation syntax into `config.yaml` was considered and rejected — it would bind the pipeline's config to one CLI's flags. The one thing a skill cannot know is supplied at the invocation (`--append-system-prompt`): that the run is unattended, so a turn must not end on a question or an unkept promise. Deliberately absent from it is any instruction to verify or re-check — current models do that unprompted, and asking compounds into wasted work.
- **The filesystem this is developed on folds case; CI runs one that does not.** macOS resolves
  `Wiki` to a `wiki/` directory and APFS folds NFC against NFD, so a page's path, a configured
  `vault.dirs` root, and two roots that look distinct can all mean something different on Linux.
  A test that writes down the local answer passes here and fails there — which is how two of
  them shipped. Run the suite against a case-sensitive volume before believing it:
  `hdiutil create -size 500m -fs "Case-sensitive APFS" -volname CS -quiet /tmp/cs.dmg && hdiutil
  attach /tmp/cs.dmg -mountpoint /tmp/cs && mkdir -p /tmp/cs/tmp && TMPDIR=/tmp/cs/tmp cargo
  nextest run --workspace`. That volume still folds NFC against NFD, so the normalization half
  needs real Linux. Where a behaviour legitimately differs, probe rather than assume — the
  `filesystem_folds_case` helper in `commands::validate::tests` is the shape.
- **A view a skill reads is a CONTRACT, not a rendering.** The user does not type these
  commands — a skill does, on their behalf — so `lore agenda --json` carries every section the
  terminal shows, with dates unformatted and the origin URL a task came from resolved, and
  `lore-day` is the skill that runs the day off it. Asking an agent to parse aligned columns is
  the same mistake `lore queue count` and `lore config vault-root` exist to prevent, and the
  columns exist to be scanned by eye. A ticked line carries `done`, because a finished task reported as today's business is what the contract exists to prevent. `lk_core::link::first_external_dest` is the mirror of the
  graph's own extraction: a task's origin is external precisely so the graph never sees it,
  which means the graph's extractor cannot be what reads it back.
- **Every column is padded by DISPLAY WIDTH.** `{:<n}` counts `char`s, and a Hangul syllable, a
  CJK ideograph, a kana and an emoji each take two columns — so a Korean vault's every list came
  out ragged, with the annotation landing wherever the titles happened to end. `commands::pad`
  measures through UAX#11 rather than a range table written here, because "which characters are
  wide" gains answers per Unicode release. Over-long text is returned whole: a clipped title is
  one nobody can search for, and the column exists to align the common case rather than to
  enforce a width.
- **`lore schedule` emits cron OR launchd** (`--format`). On macOS launchd is correct: `StartCalendarInterval` runs a job missed during sleep as soon as the machine wakes, whereas cron silently skips it — and a closed laptop at 09:00 is the normal case. Cron syntax launchd cannot express (`*/5`, `1-5`) is REFUSED, never approximated, since a silently different schedule is worse than a rejected one — what is refused is a TRANSLATION, so a job whose schedule is natively a repeat (the reminder timer) emits `*/5 * * * *` for cron and `StartInterval` for launchd, each in its own vocabulary; every emitted path must be absolute (`--bin`, `--pipeline-dir`) because launchd searches no `PATH` and expands no `~`.
- **`--pipeline-dir` is what schedules the pipelines rather than their first stage.** `lore ingest` and `lore synthesis weekly` are stage ONE of `lore-daily.sh`/`lore-weekly.sh`; the queue drain and `lore queue apply` exist only in the scripts, so scheduling the bare subcommands ingests every morning and never fills a summary or materializes a concept. With the flag those two jobs run the scripts (and only those two — the janitors and monthly+ syntheses have no LLM stage, which is why the scripts say they belong on their own schedules). A scheduled job starts with almost no environment, so the emitted entry also carries `PATH`/`LORE_BIN`/`LORE_CONFIG`/`CLAUDE_BIN` — all INHERITED from the interactive session `lore schedule` runs in, never invented, since a guessed value reproduces exactly the silently-broken job the flag exists to prevent. The REMINDER timer is a shipped script, so without the flag there is nowhere to point it and no timer is emitted — in silence, with every reminder added afterwards never firing and no `lore status` row covering a job that was never scheduled, so it is said at the one moment the answer is knowable. And the `--bin` refusal carries every flag that was passed back into its suggestion: the bare form dropped `--pipeline-dir`, and following it verbatim produced exactly the install this prevents.
- **One all-source ingest is the scheduling unit**: the work-log is a cross-source daily aggregate, so `ingest.schedule` is the single ingest cron key and `lore schedule` emits ONE `lore ingest` line — never per source. The work-log renders only on a full ingest: a filtered `lore ingest <source>` sees a structural subset of personal events and never rewrites the cross-source page (a transient source failure inside a full run still writes — loud non-zero exit, complete again on the next full run).
- **Daily pages re-render in full each run; STREAMING sources project from an event log.** A complete-refetch source (Gmail/Jira/Calendar/Slack/Drive) reproduces its whole window on demand and renders from the fetch. A streaming source (RSS — `SourceType::descriptor().streaming`, a rolling capped feed) can't, so it projects from a durable per-date event log (`.lorekeeper/events/{source}/{date}.jsonl`, raw pre-LLM events): each run UNIONs fetch + stored log (`EventId` key, fresh wins), so a scrolled-out item is never lost and a deleted page self-heals (`lore ingest --date <past>` repairs any day). Raw-layer duplication is provenance; convergence happens at the concept/graph layer (one concept = one page).
- **Every LLM-owned section in the vault is a materialized view, the concept synthesis included.** Each has an input key recording what it is owed against and a `_done` companion recording what it was written from, and `llm_cache::lookup` compares only those two — never whether the body looks filled. What differs for a concept is who computes the input: a daily page's is computed by the render that writes it, while a concept's is the citation set, which only `backlinks-sync` derives. So that sweep records it and queues the rewrite, the drain writes the section and stamps the marker, and a concept cited by thirty pages over eight months answers with a synthesis written from thirty rather than from the first one. A page that already held written prose when the sweep first saw it is ADOPTED rather than replaced — its text stands as the answer for the evidence it carries, and the rewrite is owed from the next move — because the alternative is an upgrade that replaces every authored synthesis in the vault unattended. The sequence is why `sync_graph` drains twice: the citations only exist after `queue apply`, and leaving the rewrite for tomorrow would put every concept page a day behind its own sources and leave a queue file pending at every ingest, whose startup warning would then never clear.
- **Daily pages are materialized views**: structural fields (frontmatter, raw event list, headings) are re-rendered every ingest; semantic fields (summary, refined events, concept links) are LLM-owned, preserved across re-renders, and invalidated by a BLAKE3-128 hash in the page's `llm_inputs` frontmatter — so re-ingesting unchanged data enqueues zero LLM tasks. Completion detection and cache-shape mechanics live in `lk-pipeline`.
- **A citation is created by the same act that creates the concept page, so it lasts as long as the page does.** Concept links are the one LLM-owned section whose result creates durable pages OUTSIDE the page carrying it, and `backlinks-sync` re-derives every one of those pages' sources section and `source_count` from exactly those forward links. A section that restated the newest extraction would therefore not merely drop a link: it would strip a page that still asserts knowledge of the evidence justifying it, permanently, since nothing else records what the superseded extraction had cited. So a page's concept links only ever ACCUMULATE — one rule (`render::accumulate_concepts`) applied by both writers, the plan render and `lore queue apply` — while every other LLM section states something about its own input and is replaced wholesale. What accumulating rests on is that a page's set of OBSERVATIONS only grows — a streaming source unions each fetch into that date's event log, a complete-refetch source's date is a closed window — NOT on any one observation's text being fixed, which for every adapter but `confluence` and `manual` (the two that key identity to content) it is not. So a concept extracted before an in-place edit keeps its citation after it: the citation records that this page's material named the concept when observed, which stays true, and the alternative is the loss above. Carried links are read back at the address the link builder writes, which is narrower than the graph's edge gate on purpose — a nested destination re-rendered through that builder would resolve nowhere, and the pipeline never writes one.
- **The vault at rest is an Open Knowledge Format bundle.** Every page carries a `type` frontmatter field naming its page format (`concept`, `daily`, `document`, … — the AGENTS.md format ids; OKF's one required key), and every internal reference is an inline markdown link `[Display](relative/path.md)` — destination relative to the containing page, `.md`-suffixed, CommonMark percent-encoded — the one form Obsidian, GitHub, and OKF consumers all resolve. Never `[[wikilinks]]`. `lk_core::link` single-sources the whole vocabulary (build/extract/rewrite/resolve), and `render::concepts_dir_dest` computes a page's concept-link base once so nothing downstream does path arithmetic. Rewriters (merge/normalize) match destinations at the id level (`path_slug`) with the same `.md` gate as extraction, so the set of links they repoint is definitionally the set scan counts as edges. `okf_version` stays undeclared by design (it may only live in a bundle-root index.md, which would claim a file in the user's vault root; the spec mandates best-effort consumption without it).
- **Domain logic single-sourced in lk-core**: slugify (NFKC) + `identity_key` (slugify keeping only the separators that mean something — the identity a name claims, as opposed to the address it is written at. Every break is typography — `Vector DB`/`vector-db`/`vectordb` are one name, as are `claude-35`/`claude35` — except one between two NUMERALS, which is the name, since positional notation makes `3-5` two numerals and `35` one, so `Claude 3.5` ≠ `Claude 35`. Shared by the pipeline's alias index and the graph's duplicate lint so the two cannot disagree on what "the same name" is — and because the index ACTS on that answer while the lint only reports it, the fold has to be one no reviewer would overturn), frontmatter, link, blank-line collapsing, atomic file write (`fs::write_atomic` — temp+fsync+rename+dir-fsync with a per-writer-unique temp; the one sync atomic writer every crate uses, `lk_vault::VaultWriter` being its async sibling). Zero duplicate implementations across crates. (Rich-text→Markdown conversion — ADF/HTML/Slack — is single-sourced separately in `lk-source::markdown`.)
- **READ tolerates any locale's heading; only WRITE uses the current one.** A `vault.locale` switch renames every heading at once, so a reader that searched only the new spelling finds no body to preserve and none to report — and overwrites an answered section with an empty one, on every page in the vault, reporting a clean run. `lk_vault::resolve_section` is that reader, once: it answers with the spelling the page actually carries, preferring a non-blank body over a blank one (mid-switch a page carries both, and the answer must not be the thing dropped) while still answering with a blank one when it is the only one there (a section can be legitimately empty, and calling it absent would re-enqueue it forever). Every consumer — the render's preserved bodies, the cache lookup, the citation sweep, the catalog, the synthesis rollup, the merge guard — goes through it, so the rule cannot hold in one place and not another.
- **A credential in a page is reported, never rewritten.** `lore doctor` names the forms whose issuer publishes a grammar (a reserved prefix plus that issuer's alphabet at the width it mints); anything unprefixed is out of scope BY CONSTRUCTION, because nothing in free text tells a key from a hash and a check that guessed would fire on every commit id. Rotation at the issuer is the repair — it invalidates every copy at once, where editing the page only makes the leak harder to find and leaves the vault asserting something no source said.
- **i18n single source of truth**: `vault.locale` (ko/en) switches all labels. Templates use `{{ i18n.* }}`. `lore schema` generates `<wiki>/AGENTS.md` with its page-format **headings/labels** drawn from the i18n bundle, while its structural/instructional **prose stays English by design** (an agent-facing spec; only the vault tokens it cites are localized). Source content is never translated.
- **`--dry-run` is side-effect-free**: no vault writes, no log.

## Naming conventions

Single-sourced so new code reads like existing code without guessing:

- **Constructors**: `new` (cheap, infallible-or-trivially-validating field construction — no I/O, no sub-system building) · `from_*` (convert ONE value, e.g. `Locale::from_tag`) · `build_*` / `::build` (computed/fallible construction — I/O, sub-object construction, or derivation; free fn OR associated method, e.g. `build_source`, `build_index`, `WikiGraph::build`, `VaultExistence::build`, `TemplateEngine::build`, `PipelineContext::build`) · `with_*` (builder mutator). Test-fixture factories use `build_*` (e.g. `build_event`, `build_page`) — never an off-vocabulary verb like `make_*`.
- **Accessors**: `find_*` (search, may return empty) · `load_*` (read from disk/IO, e.g. `load_config`, `Credentials::load`/`load_file`) · `resolve_*` (name → value/address) · `get_*` (in-memory present accessor) · `lookup` (keyed cache query).
- **Return types**: `*Result` = domain computation outcome · `*Report` = a CLI-facing presentation of one (lk-graph `output.rs`), introduced ONLY when display adds fields/structure beyond the `*Result` (counts, applied/fixed flags); a display-ready `*Result` (e.g. `ClusterResult`, `MergeResult`) is printed directly — an empty pass-through `*Report` is ceremony, not consistency.
- **Predicates** `is_*` (state) / `has_*` (possession), always prefixed (e.g. `is_resolvable`, not `resolves`). Each crate's public error SURFACE is a domain-named, typed `<Crate>Error` (a leaf parse/validate helper may return a `String` message that a caller wraps into its typed error — the payload is text, the surface is not); most crates have a single `<Crate>Error`, but a foundational crate may carry several domain errors (lk-core `ConfigError`). Enum variants PascalCase, `#[serde(rename_all = "kebab-case")]` on the wire · types spell words in full (`GraphCommand`, `CategoryReference`, `PipelineContext` — never `Cmd`/`Ref`/`Ctx`), locals may abbreviate (`ctx`).
